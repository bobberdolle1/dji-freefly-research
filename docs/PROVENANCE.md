Stage 1 of the Free Fly reverse-engineering project.

the method that produced it), **INFERENCE** (a conclusion from facts, with the
reasoning stated), or **HYPOTHESIS** (a guess, with what would confirm it).

```
python tools/baseline.py samples/FF_v_1_00.apk work/baseline
python tools/signing.py samples/FF_v_1_00.apk work/baseline
```

**FACT.** `android.permission.INTERNET` is **absent**.

The single permission is the AndroidX-generated signature-level permission used
to hand out private broadcast receivers to other components of the same app; it

## 4. Network and licensing — the decisive evidence

The brief asked us to confirm or refute a remote licence backend. Three
independent lines of evidence all agree.

**FACT — permission.** No `android.permission.INTERNET`. On Android that
permission is what gates the socket syscalls, so the app holds no direct
capability to open a TCP or UDP connection.

**FACT — no HTTP stack in the DEX.** A class-presence scan over all ten DEX
files (apktool smali) found zero classes for:

| Library | Classes found |
|---|---|
| `okhttp3` | 0 |
| `retrofit2` | 0 |
| `com/google/gson` | 0 |
| `org/apache/http` | 0 |
| `com/squareup/picasso` | 0 |
| `com/bumptech/glide` | 0 |
| `com/google/firebase` | 0 |

For contrast, `kotlinx/coroutines` is present (877 files) and `androidx/hilt`
is present — the scan method detects what is actually there.

**FACT — no endpoints.** `tools/baseline.py` scanned every DEX file, every
native library, and every text asset for URL and e-mail patterns. The complete
result is 8 distinct URLs, all of which are third-party build metadata:

| Count | URL | Classification |
|---|---|---|
| 32 | `http://schemas.android.com/apk/res/android` | Android XML namespace |
| 4 | `https://android.googlesource.com/toolchain/llvm-project` | Kotlin/AndroidX metadata |
| 1 | `https://goo.gle/compose-feedback` | Compose library string |
| 1 | `http://www.w3.org/2000/svg` | SVG namespace |
| 1 | `https://issuetracker.google.com/issues/297974033` | AndroidX issue link |
| 1 | `https://issuetracker.google.com/issues/300280216` | AndroidX issue link |
| 1 | `http://schemas.android.com/tools` | Android XML namespace |
| 1 | `https://youtrack.jetbrains.com/issue/KT-55980` | Kotlin issue link |

The single e-mail-shaped match, `q@R.pt`, is a false positive from binary data.

**Conclusion — FACT.** There is **no** remote licence backend, **no** update
service, **no** telemetry, **no** analytics, **no** crash reporting and **no**
authentication of any kind.

**Scope of that conclusion — stated precisely.** The finding is *no direct
Android Internet capability, and no embedded remote backend*. Three channels
have **not** been excluded and are not claimed to be: Binder, intent and
broadcast IPC to a cooperating process; a local content provider or
`LocalSocket` exposed by another installed app; and USB itself. The last is
live — the app declares `android.hardware.usb.host` and registers
`USB_DEVICE_ATTACHED`, so USB bulk/serial traffic is a genuine egress path from
the device. What that traffic reaches is a DJI controller or flight controller,
not a remote server, so it does not create a phone-home channel; but it does
mean "no data leaves the device" would be an overclaim, and it is not made.

**INFERENCE.** Any claim that this build "works without a licence" is trivially
true and uninteresting: there is nothing to check a licence against. Whatever
the author's intent, this artefact enforces nothing remotely, because it holds
no socket capability and carries no remote backend to talk to.

## 5. USB, transports and exported components

**FACT.** Declared USB hardware support:

```xml
<uses-feature android:name="android.hardware.usb.host"/>
```

**FACT.** `res/xml/device_filter.xml`:

```xml
<usb-device product-id="32" vendor-id="11427" />
<usb-device product-id="16" vendor-id="11427" />
<usb-device product-id="24" vendor-id="11427" />
```

Vendor ID `11427` = `0x2CA3`, DJI Innovation's USB vendor ID. Product IDs
`0x20`, `0x10`, `0x18` (32, 16, 24 decimal). **INFERENCE:** these are the
USB-serial/CDC-ACM product IDs of DJI remote controllers (the RC-N1/N2/N3
family and/or smart controllers). Which specific devices map to which product ID
is determined in Stage 5 from code, not guessed here.

**FACT — exported components.**

| Component | Exported | Notes |
|---|---|---|
| `com.dronehacks.app.MainActivity` | yes | `MAIN`/`LAUNCHER` + `USB_DEVICE_ATTACHED`; auto-launches on controller attach |
| `androidx.compose.ui.tooling.PreviewActivity` | yes | Compose tooling preview activity (dev-only class, shipped in the debug build) |
| `androidx.profileinstaller.ProfileInstallReceiver` | yes | guarded by `android.permission.DUMP` |
| `androidx.startup.InitializationProvider` | no | Emoji2 / ProcessLifecycle / ProfileInstaller initialisers |

**FACT.** No `<service>` and no `ContentProvider` authored by `com.dronehacks.app`.
No Android Open Accessory (`USB_ACCESSORY_ATTACHED`) filter, no `UsbAccessory`
manifest metadata. **INFERENCE:** the app talks to the aircraft as a **USB host**
over a serial-class interface, not as an AOA accessory. The phone-side app cannot
be an AOA accessory here because the aircraft-side accessory support would have
to live in different hardware/firmware.

## 7. Signing

**FACT** (`tools/signing.py`, cross-checked with `openssl x509`):

| Field | Value |
|---|---|
| JAR/v1 signature | **absent** — no `META-INF/*.RSA`, `*.DSA`, `*.EC`, `*.SF` |
| v2 signature block | present, id `0x7109871A`, length 1394 |
| v3 / v3.1 | absent |
| Verity padding block | present, id `0x42726577`, length 2654 (zero-filled, no `verB` magic) |

Signing block layout, verified against this file and pinned by
`tests/test_signing.py`:

```
[ pairs ][ uint64 size ][ 16-byte magic "APK Sig Block 42" ][ central dir ]
```

`size = len(pairs) + 24`, so the pairs start at `central_directory_offset - size`
and end at `central_directory_offset - 24`, immediately before the footer. Each
pair is `uint64 length; uint32 id; value[length-4]` — note the id is **uint32**,
not uint64; reading it as uint64 silently consumes four bytes of value and
shifts every subsequent pair. The walk terminates exactly at the footer with
both copies of `size` equal.

The parser reads certificate fields via `openssl x509` rather than a
hand-rolled DER walk: X.509 is not the research subject here, and a bespoke
parser with an off-by-one silently produces wrong provenance evidence.

**FACT — certificate:**

| Field | Value |
|---|---|
| Subject / Issuer | `CN=Android Debug, O=Android, C=US` (self-signed) |
| Serial | `01` |
| Validity | `2026-05-31 10:22:30 GMT` → `2056-05-23 10:22:30 GMT` |
| DER SHA-256 | `a3239282c4a6068656e4f1f2474cb1c4ae162bc2ec7e57e97f5a8340b845893c` |
| DER SHA-1 | `e196cb5b96b94d55292f6bb69df3cab6430f13d8` |
| Public key SHA-256 | `d792dd0c362ed4a16978913710a7433c303f82de5f5961a86a626de34a1ef563` |
| Signature algorithm | `1.2.840.113549.1.1.11` (sha256WithRSAEncryption) |

**FACT.** `android:debuggable="true"`, and the APK is signed with the **standard
AOSP Android debug keystore certificate** (`CN=Android Debug`). The validity start
date of 2026-05-31 shows the debug keystore was generated roughly five months
before this build.

**INFERENCE.** This is an unreleased developer/debug build, sideloaded rather
than distributed through a store. It was never intended to ship to end users, and
the developer took no step to protect it.

## 8. Obfuscation, dynamic loading, anti-analysis

**FACT — obfuscation: none on app code.** All 258 `com/dronehacks/**` classes
retain full human-readable names. Sampled: `DroneHacksApp`, `MainActivity`,
`DroneRepository`, `UsbSerialManager`, `DroneCommands`, `DumlBuilder`,
`DumlParser`, `DumlHeader`, `DumlPacket`, `DumlConstants`, `ParamCatalog`,
`ParamDef`, `ParamType`, `ParamValueType`, `ParamCategory`, `DroneInfo`,
`DroneParameter`, `ConnectionState`. No single-letter class or method names, no
string encryption, no control-flow flattening.

The remaining `com.dronehacks` classes are Hilt/Dagger-generated
(`DaggerDroneHacksApp_HiltComponents_*`, `DroneHacksApp_HiltComponents$*`,
`Hilt_*`, `ComposableSingletons*`) or R classes — all mechanically generated,
not hand-obfuscated.

**FACT — dynamic loading.** Keyword scan across all DEX, native libraries and
text assets: `loadClass` appears once; `DexClassLoader`, `InMemoryDexClassLoader`,
`nativeLoad` and `System.loadLibrary` do not appear. The single `loadClass` hit is
AndroidX/Hilt infrastructure, not app logic. **INFERENCE:** no dynamic code
loading; all protocol code is statically present in the DEX.

**FACT — anti-analysis.** No `ptrace`, no `frida`, no `xposed`, no
`isDebuggerConnected`, no emulator/VM detection, no integrity self-check, no
packer. (Apparent "xposed"/"frida" hits in the raw keyword count come from
unrelated binary data inside libraries, not from app code; the app's own smali
contains no such references.) The Compose `PreviewActivity` and
`ProfileInstallReceiver` being present are the opposite of anti-analysis — they
are developer conveniences shipped in a debug build.

## 9. Is this Drone-Hacks code?

The package name is `com.dronehacks.app`, the theme is `Theme.DroneHacks`, and
the application class is `DroneHacksApp`. That is a strong *hint* of Drone-Hacks
authorship, and it is not nothing — but the brief is right to insist it is not
proof.

**What the evidence supports:**

- **FACT.** The app's own identifiers consistently say "Drone-Hacks"
  (package, application class, theme, `DeviceTreeDeps` class), while the
  user-visible label says "Free Fly".
- **FACT.** The app is a Compose + Hilt + coroutines Android app using the USB
  host serial path and a bundled `assets/params_catalog.json`.
- **INFERENCE.** The most probable reading is that this is a Drone-Hacks-family
  Android client, renamed for distribution as "Free Fly", sharing authorship or
  codebase with the Drone-Hacks project.
- **HYPOTHESIS.** "Free Fly" is a rebranded or a reduced rebuild of Drone-Hacks'
  Android client. Confirming this requires a code-level comparison against the
  Drone-Hacks 1.48 Windows binary (`dh_v1.48_signed.exe`, tracked separately in
  `research/corpus/`), not an inference from names.

**What is NOT claimed:** no copied code is asserted at this stage. Under the
provenance scale used throughout this project, shared branding is **LOW**
evidence. Only identical uncommon code, identical large constant tables,
identical bugs, identical unusual packet construction, or identical strings with
the same typos would justify a HIGH claim. Stage 4/7 collects that evidence.
